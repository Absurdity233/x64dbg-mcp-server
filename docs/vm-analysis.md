# 虚拟化保护代码的解读方案

面向 Snarl 3.1.0 这类目标：`.text` 之外有一个 ~237 MB 的 `.#yU` 段，控制流是
**异常驱动**的，真实逻辑被翻译成一串 handler 调用，静态反编译基本失效。

本文给出可落地的分析流程，以及每一步需要的工具和已具备的能力。

---

## 0. 先明确可行性边界

虚拟机保护不等于不可分析，但**不可能一键还原**。能自动化的是：

| 能做 | 不能做 |
|---|---|
| 定位 dispatcher（分派器） | 自动还原成可读的 C 代码 |
| 切分并聚类 handler | 绕过服务端授权（已确认服务端裁定） |
| 统计每个 handler 的调用频次 | 猜出加密密钥（如果密钥在服务端） |
| 恢复 handler 的寄存器语义 | 完全理解混淆后的算术等价变换 |
| 生成 handler 的伪代码骨架 | |

目标产物是**语义地图**：哪些 handler 负责算术、哪些负责内存访问、哪些是
控制流，以及它们之间的调用关系。有了这张图，定位"哪个 handler 在处理
激活码"就从盲搜变成查表。

## 1. 数据来源：带寄存器快照的执行轨迹

x64dbg 的 trace 日志格式由 `TraceSetLog` 的格式串决定，可以塞任意表达式：

```
TraceSetLogFile "F:\reverse1\captures\trace.csv"
TraceSetLog "{p:cip},{p:rax},{p:rbx},{p:rcx},{p:rdx},{p:rsi},{p:rdi},{p:rsp},{p:rbp}"
TraceIntoConditional 0, 5000000
```

关键点（都实测过）：

- **条件参数是"中断条件"，不是"继续条件"**。`0` = 永不中断，`1` = 立即中断。
  写错会让 trace 只有一行。
- `TraceIntoConditional` 是异步的，启动后要等它自己结束或显式 `stop`。
- 一次 300 步的 trace 产生 768 行 —— 因为 x64dbg 会在部分指令上重复记录。
  真实目标需要 **百万级** 采样，文件会到 GB 量级。

已验证：`F:\reverse1\captures\trace_test.csv`（768 行，cip/rax/rcx）。

## 2. 分析流水线

```
trace.csv
   │
   ├─[1] 归一化       去重、按 tick 排序、解析十六进制
   │
   ├─[2] 定位 dispatcher  找"被反复跳回的地址"
   │
   ├─[3] 切分 handler     以 dispatcher 为界，切成 handler 片段
   │
   ├─[4] 聚类            按指令序列哈希分组 → handler ID
   │
   ├─[5] 语义分类        按寄存器读写模式判断 handler 类型
   │
   └─[6] 出图            handler 表 + 调用频次 + 跳转关系
```

### [2] 定位 dispatcher

虚拟机的形态：handler 执行完，把下一个 handler 的地址写进某个寄存器
（或栈槽），然后 `jmp` 回同一个分派点。

判据（按可靠性排序）：

1. **高频回访地址**：trace 里出现次数最多、且与其它地址呈"星形"连接的地址。
2. **周期性**：CIP 序列中该地址的间隔分布集中。
3. **前驱多样性**：指向它的前驱地址数量远大于它自己的后继数量（1 个）。

### [3] 切分 handler

以 dispatcher 的每次出现为分隔点。每个片段 = 一次 handler 执行。

注意异常驱动的目标：片段边界可能落在 `int3`/异常处理返回处，需要把
`exception` 事件也纳入切分依据（我们的 MCP 已经能拿到）。

### [4] 聚类

对每个片段的**指令地址序列**取哈希（不含操作数，避免被立即数干扰）。
同一 handler 每次执行的地址序列相同，哈希即 handler ID。

变体处理：
- 指令序列相同但长度不同的，归为同一 handler 的不同路径
- 用 `(序列哈希, 长度桶)` 作为二级键

### [5] 语义分类

对每个 handler 聚类，统计寄存器读写：

| 模式 | 推断 |
|---|---|
| 只读 `rsp`/`rbp` 相对地址并写内存 | **store**（写变量） |
| 读内存 + 写 `rax` | **load**（读变量） |
| 两个操作数 → 一个结果，无内存访问 | **算术**（加减异或等，需进一步区分） |
| 修改 `eflags` 且后继不唯一 | **条件分支** |
| 把常量写入栈槽且后继跳转到计算出的地址 | **push/jmp**（控制流） |
| 调用外部 API | **native call**（VM 出口，最有价值） |

**VM 出口**是优先目标：找到"从 VM 跳回原生代码"的 handler，就能定位
被虚拟化的功能边界。

## 3. 需要的工具（按优先级）

| 工具 | 状态 | 说明 |
|---|---|---|
| `trace` 落盘 | ✅ 已有 | `x64dbg_tracing log_setup` + `into`，刚修好默认条件 |
| trace 解析器 | 🔧 本仓库 `scripts/trace_analyze.py` | 原型，见下 |
| 长 trace 分片 | ❌ 缺 | 单文件 GB 级要分片写、分片读 |
| 异常感知切分 | ❌ 缺 | 需要把事件流和 trace 对齐 |
| handler 伪代码生成 | ❌ 缺 | 可选，接 IDA/Ghidra 反编译单个 handler |
| 调用图可视化 | ❌ 缺 | 输出 DOT/Mermaid |

---

## 4. 原型：`scripts/trace_analyze.py`

已实现第一阶段（[1]–[4]）：

```bash
python scripts/trace_analyze.py trace.csv --columns cip,rax,rcx
```

输出：

```
总步数 / 唯一地址数 / dispatcher 候选（含回访次数）
handler 表：ID, 入口地址, 指令数, 命中次数, 占比
```

这一步能直接回答："这个 VM 有多少个 handler、哪个最热"。

---

## 5. 分阶段目标

| 阶段 | 产出 | 判断标准 |
|---|---|---|
| P1 | dispatcher + handler 数量 | handler 数稳定，不随 trace 长度变化 |
| P2 | handler 频次分布 | 符合长尾（少数热 handler = 循环/分派） |
| P3 | 语义分类 | 至少识别出 load/store/算术/分支四类 |
| P4 | VM 出口定位 | 找到调用 Win32 API 的 handler |
| P5 | 关键 handler 定位 | 定位处理"激活码字符串"的 handler |

P1–P3 可以完全自动化。P4 需要人工确认出口的语义。P5 是最终目标，
依赖前四步。

---

## 6. 现实预期

以 Snarl 的规模（237 MB 保护段、异常驱动），即使工具链完备：

- P1–P2：几小时（trace + 聚类）
- P3：需要多轮验证，可能几天
- P5：**不保证成功** —— 如果关键逻辑在服务端，VM 里只有协议编码

已知结论（来自 `Snarl-3.1.0-reversing-report.md`）：授权由
`gateway.snarl.today` 裁定，本地只有"构造请求 / 解析响应"。所以 VM 分析
的现实目标是**搞清楚请求里那 201 字节密文是怎么来的**，而不是找本地分支。
